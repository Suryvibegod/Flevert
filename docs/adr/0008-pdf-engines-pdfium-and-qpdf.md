# ADR-0008: PDF with a current pdfium and qpdf, fetched by pinned hash

## Status

Accepted

## Date

2026-10-20

## Context

v0.2 adds PDF operations (docs/specs/pdf.md). PDFs arrive from strangers by chat and email, so whatever parses them must be maintained and patched. Flevert is MIT and links nothing under the GPL or AGPL. Binaries must never be committed (CLAUDE.md), and releases are built only by GitHub Actions (ADR-0005).

Options checked on 2026-10-20:

- Ghostscript, MuPDF, iText: AGPL. PDFsharp: AGPL from 6.5; earlier versions are MIT but unmaintained.
- Magick.NET reads PDF only through Ghostscript, and its PDF writer re-encodes images.
- `Docnet.Core` (last release 2023-09) and `PDFiumCore` (around Chromium 4688, 2021) are MIT/Apache wrappers that bundle pdfium builds years behind on security fixes.
- `bblanchon/pdfium-binaries` publishes pdfium builds for each Chromium branch (MIT build scripts, pdfium BSD-3-Clause with its third-party licences in the archive). pdfium can render, extract text and images, create documents (`fpdf_edit.h`), and save; it cannot encrypt.
- qpdf (Apache-2.0) does structural work (rotate, merge, split, compress, remove metadata, encrypt and decrypt, repair) from the command line. Its Windows build links OpenSSL and ships the MSVC runtime; its zip has no licence files.

## Decision

- **pdfium** `chromium/8100` (`pdfium-win-x64.tgz`) runs in-process through a small `LibraryImport` wrapper written for Flevert, behind a process-wide lock (pdfium is not thread-safe), for rendering, images to PDF, text and image extraction and image recompression.
- The wrapper (`src/Flevert.Pdf/Pdfium.cs`, `PdfiumNative.cs`, `PdfDocument.cs`) declares only the functions Flevert calls, from the public headers of the same branch, instead of taking a NuGet wrapper: the maintained ones bundle their own, older pdfium, and the declarations are a few dozen lines. Its rules:
  - `pdfium.dll` loads from the assembly's folder or System32 only (`DefaultDllImportSearchPaths`), never from the current directory.
  - `FPDF_InitLibraryWithConfig` runs once, on first use, and the library is never torn down.
  - One process-wide lock (`Pdfium.Gate`) is held around every pdfium call, closing handles included; documents, pages and bitmaps are `SafeHandle`s whose release takes the same lock, and a page keeps its document open.
  - Documents are read through `FPDF_LoadCustomDocument` with a callback over a .NET file handle, not `FPDF_LoadDocument`. Both open Unicode and `\\?\` long paths with this build (checked 2026-10-20), but with our own handle the size limit is checked on the very file pdfium reads, the file is shared for reading only while open (no one can change it under the parser), and a handle the runner already holds can be passed later. The callback is an `UnmanagedCallersOnly` function, so no delegate can be collected while pdfium holds it, and it never lets an exception reach native code.
  - Untrusted-input limits from the spec: files over 2 GB are refused before parsing, documents of more than 2 000 pages after loading, and a page renders at a lower DPI when the requested one would pass 10 000 px on a side. Renders go into a buffer Flevert allocates (at most 400 MB); `GetRenderSize` gives its size first so an operation can reserve it from the memory budget.
  - A password-protected PDF fails with "This PDF needs a password: use Remove password first", the same words as the qpdf operations.
- **Images to PDF** (`src/Flevert.Pdf/PdfBuilder.cs`) uses pdfium's creation API (`fpdf_edit.h`, `fpdf_save.h`) instead of the PDF writer of Flevert's own that the spec first planned: pdfium already lays out pages, image XObjects, content streams and the cross-reference table, and is maintained. Its rules, checked against the chromium/8100 headers and sources and by tests:
  - A JPEG is embedded as it is (DCTDecode), after `JpegSegments.Strip` removed its metadata, with `FPDFImageObj_LoadJpegFileInline`: "inline" copies the bytes into the document, so the source can go as soon as the call returns. Any other image arrives as pixels, flattened onto white (no soft mask), which pdfium stores Flate-compressed.
  - `JpegSegments` keeps an allow-list: the first JFIF APP0 (rewritten as a 16-byte header with the same version, units and density and a 0 x 0 thumbnail, unless it already is one: a JFIF thumbnail can show what was cropped out), APP2 ICC profiles, the 12 bytes of the first APP14 "Adobe", DQT, DHT, SOF0 to SOF2, SOS, DRI, RSTn and EOI. Every other APP0 (JFXX thumbnails, Canon CIFF with owner and serial, AVI1), every other application segment and COM are dropped; DAC, DHP and EXP (arithmetic or hierarchical coding) fail as not supported, any other marker as damaged.
  - pdfium only reads a JPEG's header, and libjpeg decodes a JPEG with a missing table using a default (no quantization table: black; no Huffman table: the standard tables, garbage for an optimized JPEG, which ImageMagick's full decode passes with a warning). So `JpegSegments` checks that every table a scan uses is defined before that scan (a quantization table per frame component; both Huffman tables for a sequential scan, the DC one for a first progressive DC scan, the AC one for an AC scan) and refuses the JPEG as damaged otherwise, rather than as not supported: re-encoding it would only turn the garbage into pixels. A JPEG that legitimately relies on the standard Huffman tables (some motion-JPEG frames) is refused with it.
  - pdfium gives every 4-component JPEG `/Decode [1 0 1 0 1 0 1 0]`, which is right for the inverted CMYK of Adobe and libjpeg (a test renders it: CMYK red shows as (238, 29, 35), as printed ink). Without an Adobe APP14 nothing says the CMYK is inverted, so such a JPEG fails as not supported, for the operation to re-encode.
  - `FPDFImageObj_LoadJpegFileInline` returns TRUE whatever pdfium made of the bytes (`LoadJpegHelper`; `FPDFImageObj_SetBitmap` likewise). When libjpeg cannot read the header (not a JPEG, cut before SOF or SOS, a bogus DQT index), the image is simply left without a stream and its page is saved blank. The builder therefore checks `FPDFImageObj_GetImagePixelSize`, which is only set once pdfium has read the header, against the size `JpegSegments` read from SOF, and refuses the JPEG otherwise. pdfium reads nothing past the header: a JPEG without quantization tables is embedded and renders black (pinned by a test), which is why `JpegSegments` checks the tables.
  - The image object belongs to Flevert until `FPDFPage_InsertObject`, which takes it on success and frees it on failure (`FPDF_BOOL` in the chromium/8100 header, "Ownership of |page_object| transfers to |page| on success. |page_object| is freed on failure"); on every other path Flevert destroys it. A page is added last (`FPDFPage_New` at index `PageCount`) only once its image has loaded, and deleted again if inserting the image or generating its content fails, so the page tree never holds half a page. `FPDFPage_Delete` leaves a `null` object where the page dictionary was (seen in a test that makes `GenerateContent` fail); `FPDFPage_GenerateContent` stays the last step, so a removed page's image and content stream have not been written into the document. With valid handles pdfium never fails these two calls; the builder lets a test replace `GenerateContent` to reach the path.
  - `FPDF_SaveAsCopy` (`FPDF_NO_INCREMENTAL`) writes through an `FPDF_FILEWRITE` whose `UnmanagedCallersOnly` callback writes to a .NET `Stream`. pdfium passes the callback the struct itself, so Flevert's struct carries one field of its own after pdfium's two to find its sink. An exception from the stream never crosses pdfium's frames: it is kept, the callback returns 0 (and writes nothing more), and it is rethrown as it was once `FPDF_SaveAsCopy` returns. `Pdfium.Gate` is held for the whole save, so every other pdfium call in the process waits for the stream: the operation gives it a local temporary file.
  - A page is the image at its DPI (150 when unknown, or outside 1 to 10 000), scaled down, proportions kept, to A4's long side (841.89 pt) when larger. A4 rather than Letter: its long side is the longer, so fewer pages shrink. Only the long side is bounded: a page shaped like A4 prints on Letter with "fit to page" at 94%, but a wider one shrinks more, a square page of that side to 73% on Letter and 71% on A4.
  - The EXIF orientation (1 to 8) is applied by the image's matrix (`FPDFImageObj_SetMatrix`, which takes doubles; `FPDFPageObj_SetMatrix` is experimental and takes floats), with the page's sides swapped for 5 to 8, never by re-encoding pixels. A test compares all eight with ImageMagick's AutoOrient.
  - At most 2 000 pages, as many as Flevert opens, and 100 MP per page, JPEG or bitmap, refused before pdfium sees the image. Everything added stays in memory until saved, and pdfium aborts the process when an allocation fails; its cross-reference table writes offsets with `"%010d"` (`CPDF_Creator`), so a file past 2 GB would be broken. The builder therefore counts what it holds (JPEG bytes, 3 bytes per bitmap pixel) and refuses a page that would take it past 1.5 GB, before pdfium copies anything; the other 512 MB cover what saving adds (Flate grows incompressible pixels by well under 1%, a page's dictionaries take a few hundred bytes). The operation still reserves its share of `MemoryBudget` for the builder's whole life.
  - pdfium writes `/ColorSpace /DeviceRGB` (or `DeviceGray`, `DeviceCMYK`) for a JPEG and no ICC colour space, so a kept APP2 profile changes nothing in viewers; it stays because removing it gains nothing and keeps the stream identical to the source. Decided for T11: the HEIC/HEIF/AVIF/WebP path, which re-encodes anyway, converts to sRGB first; a JPEG with another profile (Display P3 on iPhones, Adobe RGB) is embedded as it is and shows a little less saturated, as in a viewer that ignores profiles, since re-encoding every such photo would lose the byte-for-byte embedding the spec asks for.
  - The spec allows a PDF Flevert makes one piece of metadata, Producer: Flevert. pdfium has no function to set Info (`FPDF_GetMetaText` only reads), and `FPDF_CreateNewDocument` writes `/CreationDate` (local time) and `/Creator (PDFium)`. `FPDF_SetSandBoxPolicy(FPDF_POLICY_MACHINETIME_ACCESS, false)` drops the date (checked: it is process-wide, applies to other threads, and leaves rendering unchanged), but keeps Creator and gives no Producer; a qpdf pass after each save only to write Producer would cost a process and a second full write. Instead, the builder starts from an empty document of its own, three objects (catalog, empty page tree, Info `<</Producer(Flevert)>>`, no `/ID`) loaded with `FPDF_LoadCustomDocument`, and adds the pages to it: pdfium saves a loaded document's Info as it is and draws a random `/ID` for each save. One catch: pdfium writes only the objects it reaches from the trailer, and follows the trailer's references only to objects already parsed (`ObjectTreeTraverser`), so an unread Info is dropped and `/Info` left pointing at nothing, which `qpdf --check` does not report. The builder reads Producer with `FPDF_GetMetaText` right after loading, which parses it. A test reads every saved PDF with qpdf: Info is exactly `/Producer (Flevert)`, the catalog holds only `/Type` and `/Pages`, neither "PDFium" nor "CreationDate" is in the bytes, and two saves have different `/ID`s.
- **qpdf** 12.4.2 (`qpdf-12.4.2-msvc64.zip`) runs as a separate process through `ExternalTool` for structure and encryption. Passwords reach it only through standard input (`@-` for `--encrypt`, `--password-file=-` for decrypting), never the command line.
- `Qpdf` (`src/Flevert.Pdf/Qpdf.cs`) finds `qpdf.exe` next to the running program; the Flevert.Pdf project copies `deps/qpdf/bin` (qpdf, `qpdf30.dll`, the MSVC runtime) into the output of everything that references it, and the build fails with "run fetch-deps" when it is missing. Only qpdf imports those runtime DLLs; pdfium and Magick link theirs statically, so the app-local copies change nothing else. Its options go on the command line, but the input and output paths go through standard input as `@-` lines: qpdf's C runtime expands wildcards in command-line arguments, which breaks the `\\?\` paths the runner uses past 260 characters (checked 2026-10-20). Standard input is then already in use when a password is needed (T14): it has to travel in the same `@-` stream, or T14 checks that `--password-file=-` still reads it after the `@-` lines. Exit code 3 (warnings, output written) counts as success; a failure is mapped to the shared password message (asked with `--requires-password`, whose exit codes qpdf documents), an output error, or "not a PDF, or damaged", with qpdf's text in the log.
- `scripts/deps.json` pins each download (both release assets, qpdf's `LICENSE.txt` and `NOTICE.md` at tag `v12.4.2`, OpenSSL 3's `LICENSE.txt`) by SHA256; GitHub publishes a digest for release assets, and the pins match it. `scripts/fetch-deps.ps1` downloads into a fresh temporary folder, checks the hash before unpacking, keeps only listed files and changes `deps/` only after everything succeeded. CI, release and `setup-dev.ps1` run it; there is no cache, since the downloads take seconds and are checked every time.
- The installer ships `pdfium.dll`, `qpdf.exe`, `qpdf30.dll` and the MSVC runtime DLLs, and their licences go into `THIRD-PARTY-NOTICES.txt` (zlib and libjpeg-turbo, also linked into qpdf, are covered by the same licence texts pdfium ships).
- Neither binary is hash-checked at run time: the install folder is already checked to be writable only by the user and administrators, the same trust as `flevert.exe`.

## Consequences

- Updating pdfium or qpdf is a change to `deps.json` (new URL and digest) plus a test run; Dependabot cannot watch these, so RELEASING gets a monthly check for new versions. The PdfBuilder tests pin the pdfium behaviours images to PDF relies on (what a TRUE return means, which Info is saved, what a damaged JPEG gives), so an update that changes them fails there.
- The installer grows by about 16 MB unpacked.
- `qpdf.exe` and `pdfium.dll` are unsigned, like Flevert; Smart App Control may block them until releases are signed (ADR-0005).
- A pdfium crash takes `flevert.exe` down with it (in-process); qpdf failures cannot. Hardening fixtures (malicious PDFs) are part of the plan before release.
