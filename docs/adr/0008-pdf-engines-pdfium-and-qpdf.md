# ADR-0008: PDF with a current pdfium and qpdf, fetched by pinned hash

## Status

Accepted

## Date

2026-10-20

## Context

v0.2 adds PDF operations (docs/specs/pdf.md). PDFs arrive from strangers by chat and email, so whatever parses them must be maintained and patched. Flevert is MIT and links nothing under the GPL or AGPL. Binaries must never be committed (CLAUDE.md), and releases are built only by GitHub Actions (ADR-0005).

Options checked on 2026-10-20:

- Ghostscript, MuPDF, iText: AGPL. PDFsharp: AGPL from 6.5; earlier versions are MIT but unmaintained.
- Magick.NET reads PDF only through Ghostscript, and its PDF writer re-encodes images.
- `Docnet.Core` (last release 2023-09) and `PDFiumCore` (around Chromium 4688, 2021) are MIT/Apache wrappers that bundle pdfium builds years behind on security fixes.
- `bblanchon/pdfium-binaries` publishes pdfium builds for each Chromium branch (MIT build scripts, pdfium BSD-3-Clause with its third-party licences in the archive). pdfium can render, extract text and images, create documents (`fpdf_edit.h`), and save; it cannot encrypt.
- qpdf (Apache-2.0) does structural work (rotate, merge, split, compress, remove metadata, encrypt and decrypt, repair) from the command line. Its Windows build links OpenSSL and ships the MSVC runtime; its zip has no licence files.

## Decision

- **pdfium** `chromium/8100` (`pdfium-win-x64.tgz`) runs through a small `LibraryImport` wrapper written for Flevert, behind a process-wide lock (pdfium is not thread-safe), for rendering, images to PDF, text and image extraction and image recompression. Whatever **reads** an untrusted PDF runs it in a worker process (`flevert.exe pdf-worker`, "Reading untrusted PDFs in a worker" below); images to PDF, whose inputs are images, runs it in-process.
- The wrapper (`src/Flevert.Pdf/Pdfium.cs`, `PdfiumNative.cs`, `PdfDocument.cs`) declares only the functions Flevert calls, from the public headers of the same branch, instead of taking a NuGet wrapper: the maintained ones bundle their own, older pdfium, and the declarations are a few dozen lines. Its rules:
  - `pdfium.dll` loads from the assembly's folder or System32 only (`DefaultDllImportSearchPaths`), never from the current directory.
  - `FPDF_InitLibraryWithConfig` runs once, on first use, and the library is never torn down.
  - One process-wide lock (`Pdfium.Gate`) is held around every pdfium call, closing handles included; documents, pages and bitmaps are `SafeHandle`s whose release takes the same lock, and a page keeps its document open.
  - Documents are read through `FPDF_LoadCustomDocument` with a callback over a .NET file handle, not `FPDF_LoadDocument`. Both open Unicode and `\\?\` long paths with this build (checked 2026-10-20), but with our own handle the size limit is checked on the very file pdfium reads, the file is shared for reading only while open (no one can change it under the parser), and a handle the runner already holds can be passed later. The callback is an `UnmanagedCallersOnly` function, so no delegate can be collected while pdfium holds it, and it never lets an exception reach native code.
  - Untrusted-input limits from the spec: files over 2 GB are refused before parsing, documents of more than 2 000 pages after loading, and a page renders at a lower DPI when the requested one would pass 10 000 px on a side. Renders go into a buffer Flevert allocates (at most 400 MB); `GetRenderSize` gives its size first so an operation can reserve it from the memory budget.
  - A password-protected PDF fails with "This PDF needs a password: use Remove password first", the same words as the qpdf operations.
- **Images to PDF** (`src/Flevert.Pdf/PdfBuilder.cs`) uses pdfium's creation API (`fpdf_edit.h`, `fpdf_save.h`) instead of the PDF writer of Flevert's own that the spec first planned: pdfium already lays out pages, image XObjects, content streams and the cross-reference table, and is maintained. Its rules, checked against the chromium/8100 headers and sources and by tests:
  - A JPEG is embedded as it is (DCTDecode), after `JpegSegments.Strip` removed its metadata, with `FPDFImageObj_LoadJpegFileInline`: "inline" copies the bytes into the document, so the source can go as soon as the call returns. Any other image arrives as pixels, flattened onto white (no soft mask), which pdfium stores Flate-compressed.
  - `JpegSegments` keeps an allow-list: the first JFIF APP0 (rewritten as a 16-byte header with the same version, units and density and a 0 x 0 thumbnail, unless it already is one: a JFIF thumbnail can show what was cropped out), APP2 ICC profiles, the 12 bytes of the first APP14 "Adobe", DQT, DHT, SOF0 to SOF2, SOS, DRI, RSTn and EOI. Every other APP0 (JFXX thumbnails, Canon CIFF with owner and serial, AVI1), every other application segment and COM are dropped; DAC, DHP and EXP (arithmetic or hierarchical coding) fail as not supported, any other marker as damaged.
  - pdfium only reads a JPEG's header, so a missing table shows only when the page is drawn: without a quantization table libjpeg refuses to decode ("Quantization table 0x00 was not defined") and pdfium draws the image black; without a Huffman table libjpeg uses the standard tables, garbage for an optimized JPEG, which ImageMagick's full decode passes with a warning. So `JpegSegments` checks that every table a scan uses is defined before that scan (a quantization table per frame component; both Huffman tables for a sequential scan, the DC one for a first progressive DC scan, the AC one for an AC scan) and that there are at most 1 000 scans (each progressive scan makes a viewer go over the image again; libjpeg writes about ten), and refuses the JPEG as damaged otherwise, rather than as not supported: re-encoding it would only turn the garbage into pixels. A JPEG that legitimately relies on the standard Huffman tables (some motion-JPEG frames) is refused with it.
  - pdfium gives every 4-component JPEG `/Decode [1 0 1 0 1 0 1 0]`, which is right for the inverted CMYK of Adobe and libjpeg (a test renders it: CMYK red shows as (238, 29, 35), as printed ink). Without an Adobe APP14 nothing says the CMYK is inverted, so such a JPEG fails as not supported, for the operation to re-encode.
  - `FPDFImageObj_LoadJpegFileInline` returns TRUE whatever pdfium made of the bytes (`LoadJpegHelper`; `FPDFImageObj_SetBitmap` likewise). When libjpeg cannot read the header (not a JPEG, cut before SOF or SOS, a bogus DQT index), the image is simply left without a stream and its page is saved blank. The builder therefore checks `FPDFImageObj_GetImagePixelSize`, which is only set once pdfium has read the header, against the size `JpegSegments` read from SOF, and refuses the JPEG otherwise. pdfium reads nothing past the header: a JPEG without quantization tables is embedded and renders black (pinned by a test), which is why `JpegSegments` checks the tables.
  - The image object belongs to Flevert until `FPDFPage_InsertObject`, which takes it on success and frees it on failure (`FPDF_BOOL` in the chromium/8100 header, "Ownership of |page_object| transfers to |page| on success. |page_object| is freed on failure"); on every other path Flevert destroys it. A page is added last (`FPDFPage_New` at index `PageCount`) only once its image has loaded, and deleted again if inserting the image or generating its content fails, so the page tree never holds half a page. `FPDFPage_Delete` leaves a `null` object where the page dictionary was (seen in a test that makes `GenerateContent` fail); `FPDFPage_GenerateContent` stays the last step, so a removed page's image and content stream have not been written into the document. With valid handles pdfium never fails these two calls; the builder lets a test replace `GenerateContent` to reach the path.
  - `FPDF_SaveAsCopy` (`FPDF_NO_INCREMENTAL`) writes through an `FPDF_FILEWRITE` whose `UnmanagedCallersOnly` callback writes to a .NET `Stream`. pdfium passes the callback the struct itself, so Flevert's struct carries one field of its own after pdfium's two to find its sink. An exception from the stream never crosses pdfium's frames: it is kept, the callback returns 0 (and writes nothing more), and it is rethrown as it was once `FPDF_SaveAsCopy` returns. `Pdfium.Gate` is held for the whole save, so every other pdfium call in the process waits for the stream: the operation gives it a local temporary file.
  - A page is the image at its DPI (150 when unknown, or outside 1 to 10 000), scaled down, proportions kept, to A4's long side (841.89 pt) when larger. A4 rather than Letter: its long side is the longer, so fewer pages shrink. Only the long side is bounded: a page shaped like A4 prints on Letter with "fit to page" at 94%, but a wider one shrinks more, a square page of that side to 73% on Letter and 71% on A4. No side is under 3 pt (`MinPageSide`), the smallest page the PDF 1.7 reference (appendix C) has viewers accept: a very thin or tiny image (10 000 x 1 px, 1 x 1 px) gets a page of that side with the image centred on white, never stretched (T11).
  - The EXIF orientation (1 to 8) is applied by the image's matrix (`FPDFImageObj_SetMatrix`, which takes doubles; `FPDFPageObj_SetMatrix` is experimental and takes floats), with the page's sides swapped for 5 to 8, never by re-encoding pixels. A test compares all eight with ImageMagick's AutoOrient.
  - At most 2 000 pages, as many as Flevert opens, and 100 MP per page, JPEG or bitmap, refused before pdfium sees the image. Everything added stays in memory until saved, and pdfium aborts the process when an allocation fails; its cross-reference table writes offsets with `"%010d"` (`CPDF_Creator`), so a file past 2 GB would be broken. The builder therefore counts what it holds (JPEG bytes, 3 bytes per bitmap pixel) and refuses a page that would take it past 1.5 GB, before pdfium copies anything; the other 512 MB cover what saving adds (Flate grows incompressible pixels by well under 1%, a page's dictionaries take a few hundred bytes). The operation (`ImagesToPdf`, T11) still reserves its share of `MemoryBudget` for the builder's whole life: one share per page kept until the PDF is written, besides one per decode, and it fails rather than wait when a share could never fit beside those it holds (`MemoryBudget.ShareFor`). Saving goes through a stream that fails once the operation is cancelled, the only way to stop pdfium mid-save.
  - pdfium writes `/ColorSpace /DeviceRGB` (or `DeviceGray`, `DeviceCMYK`) for a JPEG and no ICC colour space, so a kept APP2 profile changes nothing in viewers; it stays because removing it gains nothing and keeps the stream identical to the source. Decided for T11: the HEIC/HEIF/AVIF/WebP path, which re-encodes anyway, converts to sRGB first; a JPEG with another profile (Display P3 on iPhones, Adobe RGB) is embedded as it is and shows a little less saturated, as in a viewer that ignores profiles, since re-encoding every such photo would lose the byte-for-byte embedding the spec asks for.
  - The spec allows a PDF Flevert makes one piece of metadata, Producer: Flevert. pdfium has no function to set Info (`FPDF_GetMetaText` only reads), and `FPDF_CreateNewDocument` writes `/CreationDate` (local time) and `/Creator (PDFium)`. `FPDF_SetSandBoxPolicy(FPDF_POLICY_MACHINETIME_ACCESS, false)` drops the date (checked: it is process-wide, applies to other threads, and leaves rendering unchanged), but keeps Creator and gives no Producer; a qpdf pass after each save only to write Producer would cost a process and a second full write. Instead, the builder starts from an empty document of its own, three objects (catalog, empty page tree, Info `<</Producer(Flevert)>>`, no `/ID`) loaded with `FPDF_LoadCustomDocument`, and adds the pages to it: pdfium saves a loaded document's Info as it is and draws a random `/ID` for each save. One catch: pdfium writes only the objects it reaches from the trailer, and follows the trailer's references only to objects already parsed (`ObjectTreeTraverser`), so an unread Info is dropped and `/Info` left pointing at nothing, which `qpdf --check` does not report. The builder reads Producer with `FPDF_GetMetaText` right after loading, which parses it. A test reads every saved PDF with qpdf: Info is exactly `/Producer (Flevert)`, the catalog holds only `/Type` and `/Pages`, neither "PDFium" nor "CreationDate" is in the bytes, and two saves have different `/ID`s.
- **qpdf** 12.4.2 (`qpdf-12.4.2-msvc64.zip`) runs as a separate process through `ExternalTool` for structure and encryption. Passwords reach it only through standard input (`@-` for `--encrypt`, `--password-file=-` for decrypting), never the command line.
- `Qpdf` (`src/Flevert.Pdf/Qpdf.cs`) finds `qpdf.exe` next to the running program; the Flevert.Pdf project copies `deps/qpdf/bin` (qpdf, `qpdf30.dll`, the MSVC runtime) into the output of everything that references it, and the build fails with "run fetch-deps" when it is missing. Only qpdf imports those runtime DLLs; pdfium and Magick link theirs statically, so the app-local copies change nothing else. Its options go on the command line, but the input and output paths go through standard input as `@-` lines: qpdf's C runtime expands wildcards in command-line arguments, which breaks the `\\?\` paths the runner uses past 260 characters (checked 2026-10-20). Standard input is then already in use when a password is needed (T14): it has to travel in the same `@-` stream, or T14 checks that `--password-file=-` still reads it after the `@-` lines. Exit code 3 (warnings, output written) counts as success; a failure is mapped to the shared password message (asked with `--requires-password`, whose exit codes qpdf documents), an output error, or "not a PDF, or damaged", with qpdf's text in the log.
- `scripts/deps.json` pins each download (both release assets, qpdf's `LICENSE.txt` and `NOTICE.md` at tag `v12.4.2`, and the licence files of zlib, libjpeg-turbo and OpenSSL at the tags of the versions in `qpdf30.dll`) by SHA256; GitHub publishes a digest for release assets, and the pins match it. `scripts/fetch-deps.ps1` downloads into a fresh temporary folder, checks the hash before unpacking, keeps only listed files and changes `deps/` only after everything succeeded. CI, release and `setup-dev.ps1` run it; there is no cache, since the downloads take seconds and are checked every time. Hardened after the first review (F4):
  - `%TEMP%` may let other accounts change what is created in it (on the maintainer's machine it grants a sandbox Modify), so the work folder is created with a protected DACL (the user, SYSTEM, Administrators) in one step, and checked to be new, private and empty. Each download is held open with read-only sharing from its hash check until it is unpacked.
  - `deps/.fetched` holds the manifest's hash and the SHA256 of every kept file, taken from the staged copies; the copies in `deps/` must match them. A run downloads nothing only when `deps/` holds exactly those files, unchanged: a deleted `pdfium.dll`, a changed file or a DLL added to `deps/qpdf/bin` (which the build copies next to `flevert.exe`) all lead to a fresh fetch.
  - Old copies and the work folder are removed without following junctions or symbolic links.
  - `setup-dev.ps1` warns, with the `icacls` command that fixes it, when other accounts can change the checkout: they could replace what is in `deps/` after the fetch, or add git hooks. It changes no permissions itself.
- The installer ships `pdfium.dll`, `qpdf.exe`, `qpdf30.dll` and the MSVC runtime DLLs, with their licences in `THIRD-PARTY-NOTICES.txt`. The `notices` list in `deps.json` names each file the build copies from `deps/` and its licence files: pdfium-binaries' `LICENSE` and `licenses/*`; qpdf's `LICENSE.txt` and `NOTICE.md`; for what qpdf links statically into `qpdf30.dll`, each library's own licence files at the tag of the version linked: zlib 1.3.2 (`LICENSE`), libjpeg-turbo 3.2.0 (`LICENSE.md` and `README.ijg`, with the sentence the IJG licence asks for) and OpenSSL 3.6.4 (`LICENSE.txt`; it has no NOTICE file); for the MSVC runtime 14.51, `installer/notices/msvc-runtime.txt`, since Microsoft publishes no plain-text licence to pin. `scripts/write-notices.ps1`, run by `build-installer.ps1`, accounts for every file in the publish folder (assets in `flevert.deps.json`, Flevert's own files, the `notices` entries) and fails on anything else, on a missing licence file and on an entry for a file the build does not ship; `NoticesScriptTests` runs the same check on every CI build against the real `deps/`, because CI never builds the installer.
  - qpdf's build has no pinned versions for these: `build-scripts/run-vcpkg` clones vcpkg at its tip and installs `zlib openssl libjpeg-turbo` on the day. The versions come from the binary and from the build itself (checked 2026-10-20): `qpdf30.dll` holds "inflate 1.3.2", "libjpeg-turbo version 3.2.0 (build 20260924)" and OpenSSL's version string "3.6.4" (its object paths name `vcpkg\buildtrees\openssl\x64-windows-static-rel`); the run that built the v12.4.2 release ("QPDF Build" 36273443816 on the tagged commit `4eba958`, job "Windows (msvc, x64)") used the artifact `distribution-vcpkg` (SHA256 `ec07f705c5e8f08ddf764dbfb54f87c7aba63d7acc3ef780642db6b3747caae0`, as the job log records), whose `x64-windows-static/vcpkg-list` reads `zlib 1.3.2#2`, `libjpeg-turbo 3.2.0#1`, `openssl 3.6.4#1` (also `libspng`, which `qpdf30.dll` does not contain) and whose headers say the same. vcpkg's copies of the three licences are byte for byte the upstream files pinned here. pdfium-binaries ships its own, different copies (pdfium chromium/8100 bundles libjpeg-turbo 3.1.0 and zlib 1.3.2.1-motley, Chromium's forks), which cover only `pdfium.dll`. `QpdfDepsTests` fails when the versions in `qpdf30.dll` no longer match the notices, or a notice borrows another build's licence files.
- How qpdf runs (review rounds 1 and 2, checked with qpdf 12.4.2 on 2026-10-20):
  - **Paths**: both always in the `\\?\` form, after `Path.GetFullPath`, since the prefix turns off Windows' normalisation (it also drops the trailing dots and spaces Windows ignores in a name). `\\?\UNC\` for a share; `\\.\`, `//?/` and `\??\` (the NT form .NET also opens as it is) are turned into `\\?\`; a path already in the `\\?\` form is left as it is, as .NET opens it. The runner gives an input under 260 characters in its plain form, and the temporary output beside it is 51 characters longer; qpdf opens a path past 260 characters only with `\\?\`. The `@-` lines are encoded with a UTF-8 encoder that throws: NTFS names may hold a lone surrogate, which the default encoder replaces with U+FFFD, naming another file (seen: a sibling of that name was rotated instead). Such a name fails with `PdfError.UnsupportedFileName` before qpdf runs; a character outside the BMP (an emoji) is a valid pair and reaches qpdf as its four UTF-8 bytes (a test with decoys named with U+FFFD in its place shows qpdf opens the right file). Options starting with `@` (a file of more options) are refused like wildcards. qpdf's messages name the files as it was given them; the prefix is removed from the detail kept for the log and errors.
  - **Environment**: qpdf's statically linked OpenSSL is its default crypto provider and opens the `OPENSSL_CONF` file even to rotate (it hashes for the document ID); a configuration can load modules and engines, and a file that never answers (a pipe) held qpdf until the timeout. Removing the variables is not enough: OpenSSL then reads the `openssl.cnf` in the folder it was built with, `C:\Program Files\Common Files\SSL`, and C: need not be the system drive, where any user can create that folder (review SA-L1). So qpdf gets `OPENSSL_CONF` pointing at an empty `openssl.cnf` shipped beside `qpdf.exe` (a text file in the repository, copied into the build and publish output, so the installer carries it), `OPENSSL_MODULES` and `OPENSSL_ENGINES` at that folder, and no `OPENSSL_CONF_INCLUDE` nor any `QPDF_*` variable (`QPDF_CRYPTO_PROVIDER` set to an unknown provider made every rotation fail). AES-256 encryption (T14) still works with the empty configuration. `ExternalTool` takes these changes as a per-call environment override; a name with `=` or `\0`, or a value with `\0`, is refused, since the environment block would read the rest as another variable.
  - **Limits**: each qpdf runs in a job that caps its committed memory and lets it start no other process (`JOB_OBJECT_LIMIT_PROCESS_MEMORY`, `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` = 1). The cap is **256 MB plus 2.5 times the input, at least 1 GB, at most 3 GB** (`Qpdf.MaxMemoryFor`): qpdf holds the object structure in memory (500 000 small pages, a 50 MB file, took 830 MB) and copies a stream it does not decode about twice over (100, 300 and 520 MB streams took 202, 602 and 1 043 MB; a flat 1 GB refused a 530 MB scan that rotated before, review DD-2), while a stream it re-encodes costs about its size. At most 3 GB so one PDF cannot take the machine; four ordinary PDFs at once (`MaxParallel`, up to 300 MB each) stay within 4 GB. Past the cap an allocation fails, nothing is killed, and qpdf may crash (stack overflow), fail, or treat the object or stream it was reading as null and exit with 3, "succeeded with warnings", having written an output that lacks it. Windows reports the refusal only as `JOB_OBJECT_MSG_PROCESS_MEMORY_LIMIT` on a completion port associated with the job (the peak counters do not show a refused allocation), so `ExternalTool` drains that port after the exit and sets `MemoryLimitExceeded`. That report is best effort and never comes when the machine itself is out of memory or an outer job refuses, so qpdf's own words count too: `: bad allocation` (MSVC) or `: std::bad_alloc` (libstdc++) in stderr (the colon keeps a file name from matching; Windows names cannot hold one). Either way `Qpdf` fails with `PdfError.NeedsTooMuchMemory` ("This PDF needs more memory than Flevert allows for it (1.6 GB): it is too large or too complex to process.", naming that file's cap), whatever the exit code; a success with more than the megabyte of stderr `ExternalTool` keeps is not trusted either. Not done: treating a success whose peak came close to the cap as suspect (SA-L2): the refused allocation never counts in the peak (522 MB of 1 024 in the failing 520 MB run).
  - **One process**: the console host Windows starts for qpdf joins its job and, on Windows 11, does not count against the limit (qpdf ran 200 times out of 200). Where a Windows version counts it, the assignment fails with `ERROR_NOT_ENOUGH_QUOTA` after Windows has ended the tool; `ExternalTool` then runs it once more without the one-process limit (the memory cap stays), says so in `ExternalToolResult.SingleProcessLimitDropped` and writes a trace warning, since running qpdf without that limit beats not running it. A tool that exits before it joins its job (`ERROR_ACCESS_DENIED` with the process gone) returns its result; any other refusal kills the tool and fails the run.
  - **Several inputs** (merge, T6): `qpdf --empty --pages <file>… -- <output>`, with every path and the `--` that ends `--pages` on `@-` (a page range may follow a file there; a `\\?\` path never reads as one). qpdf holds every input at once, so the 2 GB limit, the memory cap and the timeout go by their total size. qpdf's error names the file it failed on, as it was given (`qpdf: <path>: invalid password`, `qpdf: <path>: unable to find trailer…`); an error caused by one input becomes a `BatchInputException` naming it, with the `PdfException` that file alone would give inside, and when the error names none, each input is asked `--requires-password`.
  - **Split** (T8): `--split-pages` writes `<n>.pdf` for each page, by names anyone can predict, and opens each by name, so it writes through a link someone put there first. The temporary folder beside the input may let other accounts add entries (ADR-0007, "Holding the folder"), so qpdf writes into a subfolder created with its permissions already in place (this user, SYSTEM, Administrators, nothing inherited), and each page is copied from there under its final name with `CreateNew`. A copy, not a move: a moved file keeps the private permissions, a copy gets the folder's like any new file (probed). qpdf replaces the **first** `%d` of the output path with the page number, wherever it is (probed: a folder `a%d` beside `a1` sent page 1 into `a1`), so a path holding `%d` is refused before qpdf runs. qpdf reports nothing until it exits; progress counts the pages already in the subfolder.
- Neither binary is hash-checked at run time: the install folder is already checked to be writable only by the user and administrators, the same trust as `flevert.exe`.

## Reading untrusted PDFs in a worker (T9b, 2026-10-20)

### Context

Review round 1 (DD-H2, SA-M3, CR-4) found that pdfium, parsing and drawing PDFs from strangers inside the batch leader, could not be stopped: `FPDF_LoadPage` and `FPDF_RenderPageBitmap` take no cancel and no time limit, pdfium's own allocations are outside any budget (it aborts the process when one fails), and a crash in it ended the leader with every other file of the batch lost, silently. Success criterion 6 of the spec (a malicious PDF refused within 10 s, memory bounded) could not be met in-process. Decision F6 was to move reading into a worker process; this section records how.

A real malicious page was used to check it, not a test switch: one A4 page whose content is a single free-form triangle mesh (shading type 4) of a million triangles, each covering the page (`TestPdf.WriteStallingPage`, 60 KB). pdfium draws it in one call at about 2.5 ms a triangle at 150 DPI on the dev machine (2 000 took 5 s, 20 000 took 50 s), so about 40 minutes, at 77 MB. A page of a million full-page fills (`0 0 595 842 re f`, 42 KB) also ran past 40 s while growing past 380 MB; a tiling pattern with a 0.01 pt step was drawn in under 2 s (pdfium bounds it), so it is no test.

### Decision

- **Who runs where.** `pdf.to-jpg` and `pdf.to-png` (`PdfToImages`) start `flevert.exe pdf-worker` (`PdfWorker`, `PdfRenderWorker`); everything that opens an untrusted PDF with pdfium later (extract images and text, compress for sharing) uses the same worker. `PdfDocument`'s in-process API stays, for the worker itself and for tests. Images to PDF (`PdfBuilder`) stays in-process: its inputs are images ImageMagick has already decoded (or JPEGs whose markers `JpegSegments` checked and whose header only pdfium reads), and the document it builds is its own.
- **The command.** `pdf-worker` takes no argument and is not in the usage text. flevert.exe dispatches it right after `SafeStartup` (DLL search order, current directory), before the catalog, the run log and the unhandled-exception logger: the worker writes nothing to the user's log; the parent logs its outcome, with the worker's exit code and the end of its standard error in the exception detail (`PdfWorkerException`).
- **Its job.** `ExternalTool` runs it with the limits qpdf has: kill-on-close (it dies with flevert.exe), die on unhandled exception (no error-reporting dialog), one process (it starts none), and a committed-memory cap of **2.5 GB** (`PdfWorker.DefaultMaxMemoryBytes`): a page renders into at most 400 MB (10 000 x 10 000 BGRA), ImageMagick copies it once to encode it, and pdfium needs room for what it decodes to draw the page (a full-page 100 MP image is another 400 MB), beside the runtime. Fixed rather than scaled with the file as for qpdf: pdfium loads objects as pages need them and the worker frees each page, so the peak follows the largest page, not the file.
- **The request** goes through standard input, never the command line, which other processes of the user and process-start logging can read: a version tag, the input path, its file identity, the output folder, the format and the DPI, each as the raw UTF-16 code units of its text ended by U+0000 (`PdfRenderRequest`, at most 256 KB). Raw UTF-16 because an NTFS name may hold a lone surrogate, which UTF-8 and .NET's encoders replace with U+FFFD, naming another file (the qpdf finding SA-M1); no path holds U+0000. A request the worker cannot read, of another version, with a relative path, an unknown format or a DPI outside (0, 10 000], ends it with exit code 2 before anything is opened.
- **Reopen by path, check the identity.** The worker opens the input itself, by the path the runner pinned, rather than inheriting the parent's handle. The path is the pinned file's real path (no junction in it), and while the worker runs the parent holds the file open sharing reading only (as the runner's pin does), so nobody can change, rename or replace it, nor rename a folder above it. The parent reads the file's identity from its handle (`FILE_ID_INFO`: volume serial and 128-bit file ID; `GetFileInformationByHandle`'s 64-bit index where a file system has no 128-bit IDs, as the pin already uses there) and sends it; the worker compares it with the identity of the handle it opened and refuses any other file (exit code 2). Inheriting a handle was rejected: `Process.Start` with redirected streams makes `CreateProcess` inherit every inheritable handle, so a handle made inheritable for one worker could leak into any qpdf or worker started meanwhile on another thread; restricting inheritance to one handle (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) means calling `CreateProcess` directly, with its pipes and quoting, for nothing the identity check does not already give, and the handle value would still travel on the command line or stdin.
- **Where it writes.** The parent creates and holds the `.partial` folder (`OutputPath.WriteDirectoryAtomicallyAsync`, ADR-0007) and passes its real path; the worker writes each page there with `CreateNew` and never makes a subfolder, so the folder rules of ADR-0007 hold unchanged: on any failure, stall, crash or cancel the worker has exited (ExternalTool waits for it) before the parent deletes the folder, and nothing is left. After the worker reports it is done, the parent checks that every page it named exists before the folder is renamed.
- **What it says.** One line at a time on standard output, UTF-8: `pages <count>` once the PDF is open; `page <n> <width> <height>` before pdfium reads and draws page n at that pixel size; `busy <n>` at most twice a second while ImageMagick encodes page n (from its progress events: proof of work, not a timer); `wrote <n>`; `done <count>` and exit code 0; or, as the last line, `error <code> <message>` and exit code 1, where the code is a `PdfError` name, `Write` (a page could not be written) or `Setup` (ImageMagick could not be set up). `ExternalTool` hands each line to the parent as it is written (`standardOutputLine`, cut at 64 K characters); a line out of order or out of range kills the worker and fails the file; a line that is none of these (a native library printing) is ignored and does not hold off the watchdog.
- **Progress.** Each `page` line becomes a `FileProgress("page", n, count)`, so the window says "page 37 of 200" for a real PDF (DD-M4), and the bar moves within the file (`BatchProgressText.Bar`: 1 000 steps per file, page n started counts n - 1 pages done; review CR nit). Nothing is reported once the user has cancelled.
- **Watchdog.** The worker is killed when a step shows no progress for longer than it may take: **10 s plus 0.25 s per megapixel** of the page announced (2.2 MP at A4 and 150 DPI gives 10.5 s; 100 MP, the largest page, 35 s), reset by every `page`, `busy` and `wrote` line; opening the PDF, before `pages`, gets 10 s plus 1 s per 100 MB of file (pdfium may scan a damaged 2 GB file whole). Measured on the dev machine for an honest worst case, a 10 000 px square page with 20 000 shapes took 2.5 s to PNG and 1.6 s to JPEG end to end, worker start included, and 200 Letter pages took the same time as in-process (JPEG 5.8 s, PNG 11.8 s). The stalling page above is stopped about 10.5 s after its `page` line. A run of 6 hours in all is the backstop (`ExternalTool`'s timeout), past what 2 000 of the largest pages take.
- **Cancel** kills the worker (`ExternalTool` kills the job and waits for the exit), then the folder is deleted: under 1 s in the test, inside pdfium's draw call.
- **What the user reads.** Mapped by the parent, never taken from a crash: the job's memory report or the worker's own `NeedsTooMuchMemory` (a managed `OutOfMemoryException` or ImageMagick's resource limit) gives Qpdf's "This PDF needs more memory than Flevert allows for it (2.5 GB): …"; a password gives the shared "This PDF needs a password: use Remove password first"; any other `PdfError` keeps the worker's message (one line, at most 500 characters), such as "Page 2 of this PDF has no valid size."; the watchdog gives `PdfError.TooSlow`, "Page 3 of this PDF took too long to render: it is too complex, or made to stall PDF readers." (or "took too long to open"); an end without `done` or `error` (a crash, a kill, a broken line) gives `PdfError.ReaderFailed`, "Flevert's PDF reader stopped on page 3 of this PDF without finishing: the PDF may be damaged, or made to crash PDF readers."; `Write` an `IOException`; `Setup` an `InvalidOperationException` naming ImageMagick, so a broken configuration folder does not read as a damaged PDF; a missing flevert.exe a `FileNotFoundException`. The page named is the one announced and not yet written, or the next one, whose size the worker reads before announcing it.
- **Memory inside the worker.** One pixel buffer for every page, grown only for a larger page (`PdfDocument.RenderInto`; review CR-11, CR-12), and each page encoded straight into its file rather than into a byte array first. The per-page `MemoryBudget` reservation is gone: the leader of a PDF batch no longer holds pages, and the worker runs one page at a time under its own cap, which is what bounds it. `MaxParallel` stays 1: each worker may commit up to its cap, and a batch should not ask for several caps at once.

### Alternatives considered

- **pdfium in-process with a timeout thread**: a thread cannot stop a native call; `FPDF_RenderPageBitmap_Start`/`_Continue` (progressive rendering) pauses only between page objects, so one huge object (the mesh above) still runs to its end, and memory and crashes stay unbounded.
- **A separate worker executable**: a second program to build, sign, ship and keep in step with flevert.exe, for the same code; the hidden command reuses flevert.exe and its install-folder check.
- **A sandbox** (AppContainer, a restricted or low-integrity token, `PROCESS_CREATION_MITIGATION_POLICY`): it would also stop a compromised pdfium from reading or writing the user's files, but needs `CreateProcess` with a custom token or attribute list instead of `Process.Start`, and the worker must still write into the user's folder (a broker would). The worker runs as the user, like the leader did: this change bounds time, memory and crashes, not what exploited code can reach. Left for after v0.2.
- **A test-only switch that makes the worker sleep or allocate**: rejected for the real fixtures above (a stalling mesh, a page that needs 400 MB under a 256 MB cap), which test what an attacker can actually send. The only seams are the parent's limits (`PdfWorker.MaxMemoryBytes`, `StallTimeout`), internal, for tests.
- **A named pipe or JSON for the protocol**: standard input and output are already the pipes `ExternalTool` owns, with its caps; System.Text.Json cannot write a lone surrogate.

### Consequences

- Each PDF converted to images starts one more process: under 0.1 s (a file that is not a PDF fails in about 70 ms, worker start included), invisible next to rendering; a batch of PDFs starts one per file, one at a time.
- A page whose honest drawing takes longer than its window (10 s plus 0.25 s per megapixel without a `busy` or `page` line) is refused as "took too long". The window grows with the page's pixels; the dev machine's slowest honest page took a fifth of it.
- The worker sets up ImageMagick for itself (writing its configuration files), once per PDF instead of once per batch, so a configuration race between flevert.exe processes reaches it more often; it then fails with `Setup`, not as a damaged PDF.
- The leader of a PDF render batch loads neither pdfium nor ImageMagick: its own memory stayed about 10 MB while a 100 MP page rendered.
- Tests start the flevert.exe the solution built as the worker; the test classes that start workers share one xUnit collection, so a test can find its worker as a child of the test process by its `pdf-worker` command line.

## Consequences

- Updating pdfium or qpdf is a change to `deps.json` (new URL and digest, and the `notices` when the files change) plus a test run; Dependabot cannot watch these, so RELEASING has a monthly check for new versions, which also looks at where a new build comes from. The PdfBuilder tests pin the pdfium behaviours images to PDF relies on (what a TRUE return means, which Info is saved, what a damaged JPEG gives), so an update that changes them fails there.
- The MSVC runtime DLLs come unmodified from qpdf's release; only the three that `qpdf.exe` and `qpdf30.dll` import are kept (`msvcp140.dll`, `vcruntime140.dll`, `vcruntime140_1.dll`). Microsoft limits redistributing them to licensed Visual Studio users, under the Visual Studio licence terms ("Distributable Code"), and recommends against app-local copies for servicing reasons: they get security fixes only when qpdf's release does. **Decided 2026-10-21:** the maintainer accepts the Visual Studio Community licence terms, which cover redistributing this Distributable Code, and Flevert keeps shipping the three DLLs app-locally, so users need nothing else installed. Requiring the Visual C++ Redistributable was rejected: an extra install, often needing administrator rights, against a per-user installer that needs none. Consequence: these DLLs are updated only with qpdf, so the monthly dependency check also looks at qpdf releases for runtime security fixes.
- The installer grows by about 16 MB unpacked.
- `qpdf.exe` and `pdfium.dll` are unsigned, like Flevert; Smart App Control may block them until releases are signed (ADR-0005).
- A PDF qpdf cannot handle within its cap (1 to 3 GB, by size) is refused, even one a machine with more memory could convert; four PDFs near 2 GB at once could ask for 12 GB, and on a machine without that much the allocations fail and those files are refused the same way. No `openssl.cnf` outside Flevert's folder applies to qpdf; the one shipped must stay empty (a test checks it).
- A pdfium crash, stall or runaway allocation while reading a PDF ends only its worker, and the file fails with a message ("Reading untrusted PDFs in a worker"); qpdf failures cannot take flevert.exe down either. pdfium still runs in-process for images to PDF, on inputs that are images. More hardening fixtures (malicious PDFs) are part of the plan before release.
