# ADR-0007: Operations beyond one file in, one file out

## Status

Accepted (part 1: progress within a file and folder outputs; part 2: many inputs, one output, added by T5, and "No partial output", added by F5 after review round 1).

## Date

2026-10-20

## Context

Until v0.1 every operation took one file and wrote one file next to it, through `IOperation.RunAsync(input, ct)` and `OutputPath.WriteAtomicallyAsync`. The PDF operations of v0.2 (docs/specs/pdf.md, "Thay đổi ở core") break that shape in three ways:

1. **One file to many** (split, pages to JPG/PNG): the output is a folder of files. It must appear whole or not at all, as a single file does: Cancel or a failure must not leave a half-filled folder, and an existing folder must never be merged into.
2. **Progress inside one file**: rendering 200 pages takes long enough that "0 of 1 done" looks frozen. The window should say "page 37 of 200".
3. **Many files to one** (merge, images to PDF): part 2 below.

Every existing operation (images, dev operations) and every test calls the current contract, and other work on v0.2 runs in parallel, so the change has to leave them untouched.

## Decision (part 1)

### Folder outputs

`OutputPath.WriteDirectoryAtomicallyAsync(desiredDirectory, [keepSuffix,] write, ct)` creates a fixed-length `.flevert-<guid>.partial` folder beside the input, lets the operation fill it, and renames it **once** to the first free name with the same rules as a file (`name`, `name (1)`, …; a file or a folder with that name counts as taken; the name is shortened to fit 255 characters; a name taken between choosing and renaming is retried). The counter goes after the whole folder name, since a folder has no extension. `keepSuffix` (`" (pages)"`) is kept whole like an extension: only the part before it is shortened, so a 250-character stem gives `<shortened stem> (pages)` and `… (pages) (1)`, never `… (pa`. The rename never replaces anything, so an existing folder is never merged into. On an exception or cancellation the temporary folder is deleted, as described in "Holding the folder" below.

The operation returns the folder; the runner, the log and the notification treat it like any output path (`Done: report (pages)`).

### Holding the folder (review round 1, F1)

The first version created the folder, let it be, and on failure walked it by path. The folder sits beside the input, where other accounts may be able to write: a second NTFS drive gives Authenticated Users Modify by default, and so does `C:\Users\Public`. Such an account could rename the folder away between two pages, put a junction to the victim's Documents under its name, and a failing page or Cancel made the walk delete the victim's files. The walk also ran after a successful move, on a name that had just become free. Separately, Windows refuses to rename a folder while another program has a file in it open (access denied, even with delete sharing), and only a name clash was retried, so Defender, the search indexer, OneDrive or an Explorer thumbnail could make a 200-page render fail at the very end.

`PartialFolder` now holds the folder from creation until it is renamed or deleted. Each point below was checked by a probe on this machine (Windows 11, NTFS) rather than from memory:

- **Handle.** Right after `CreateDirectoryW` the folder is opened with `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT`, `DELETE | FILE_READ_ATTRIBUTES | FILE_WRITE_ATTRIBUTES`, sharing read and write but not delete. `GetFileInformationByHandleEx(FileAttributeTagInfo)` must show a folder that is not a name-surrogate reparse point (a junction, symbolic link or mount point; a cloud placeholder is still the folder). Probed: while the handle is held, another process can neither rename the folder (sharing violation) nor rename the folder above it (access denied), and the operation's own writes inside work as before.
- **Real path.** The handle locks the folder's *real* parents, but not a junction or symbolic link higher in the spelling the caller gave: that resolves away and can be re-pointed, and an output name built from the spelling then put the finished pages in the attacker's tree (probed in review F1, DD-H1). So right after the open the folder's real path is read from the handle (`GetFinalPathNameByHandleW`, `VOLUME_NAME_DOS`, falling back to `VOLUME_NAME_GUID` for a volume without a drive letter), and every path after that (the writer's, the listing, the deletes, the rename destination, the path returned) is built from it. The folder must also be an ordinary, empty directory through the handle; anything else (a file or a filled folder swapped in under the name) fails the output. One gap remains by design: the folder is created and opened by the caller's spelling, so a junction above re-pointed between those two calls would make it hold a folder in the junction's new target. Operations write beside their input, whose real path the runner resolved and pins, and the pin locks its parents, so the spelling they pass holds no junction; direct callers must resolve the parent first.
- **Anchor.** The handle is not enough. Anyone who can write to the folder can open it for `FILE_WRITE_ATTRIBUTES`, which sharing does not govern, and turn it into a junction in place with `FSCTL_SET_REPARSE_POINT`, as long as it is empty. Probed: this works even when the handle shares only reading, and the next page is then written into the junction's target. So a hidden `.flevert.lock` is created inside at once, with no sharing and `FILE_FLAG_DELETE_ON_CLOSE`. It is accepted only when its final path (`GetFinalPathNameByHandleW`, NT form) is inside the folder held, since it is created by path. While it is open the folder is never empty, and the conversion fails with `ERROR_DIR_NOT_EMPTY` (probed). Nobody else can open or delete it, and it disappears even if the process is killed. The writer is handed a folder holding only the anchor. If either final path cannot be read, the anchor is accepted anyway, on the assumption that a file system which cannot name an open file has no junctions either; that holds for NTFS, ReFS and FAT, but is not checked for user-mode file systems (WinFsp, Dokan), which may support reparse points.
- **Rename.** Through the handle with `SetFileInformationByHandle(FileRenameInfo)`, `ReplaceIfExists = FALSE`, and a full `\\?\` path. A bare name is resolved against the process's current directory (documented for `FILE_RENAME_INFO`, and probed: the folder moved there). The anchor is closed first, since a folder with an open file in it cannot be renamed. The extended path is not normalised, so a reserved folder name is trimmed of a trailing dot or space, and must be one Win32 reads unchanged (no device names). Afterwards the handle is checked again. If someone emptied the folder and turned it into a junction after the anchor went, the junction is what was renamed: only the link is removed, and the operation fails.
- **Retry.** While the reserved name is free, `ERROR_ACCESS_DENIED` or `ERROR_SHARING_VIOLATION` is retried for about 30 s (25, 50, 100, 200, 400, 800 ms, then 1 s at a time). Cancel stops the wait, and the folder is then deleted like any cancelled output. If the rename is still refused after that, the pages are **kept**: they are complete and only the name is missing, so deleting them would throw a long render away for a scanner's sake (review F1 round 1, DD-M1). The folder is shown again under its temporary name, `.flevert-<guid>.partial`, and the operation fails with a message naming it. Probed: with a page held open by another process, the rename fails with error 5 until it is closed, then succeeds. The first version waited 2 s and then deleted everything; a full scan or an upload of a large page can hold it longer than that.
- **Cleanup.** Only when there was no rename. If the folder itself is a link, only the link is removed. Otherwise it looks inside by path only while the anchor is held (re-created and re-checked if it was closed), because an empty folder could otherwise become a junction between the check and the listing. Each entry is opened without following links and deleted through that handle (`FileDispositionInfoEx`: POSIX semantics, ignore read-only; the classic disposition on file systems without it). So a link is unlinked and never followed, a folder is removed only when empty, and a file a scanner still has open loses its name at once. It never goes into a subfolder. The writers (`PdfToImages`, `DevSplit`) never make one, so a folder with something in it was put there by someone else, and it is left with what is in it. Last, the folder goes through its own handle; if something is still in it, it stays, and is shown and indexed again so the user finds it (it would otherwise sit hidden beside the input).
- **Hidden.** The folder is Hidden and NotContentIndexed while it is written, set through the handle, so Explorer and the indexer leave its pages alone. Files created in a NotContentIndexed folder inherit the mark (probed), so the pages lose it before the rename. Each page is changed through its own handle, while the anchor is held; an entry with more than one hard link is skipped, since a planted hard link shares a file outside the folder. After the rename the folder is shown and indexed again. If the folder beside it was already kept out of the index, the result keeps the mark, as any new folder there would. `FileBasicInfo` replaces every settable attribute, so each bit read back is sent back unless it is the one being changed, OneDrive's PINNED and UNPINNED included (probed: leaving them out of the mask cleared "Always keep on this device" on the folder and its pages).

Writers create every file with `FileMode.CreateNew`. Others can still add, open or delete entries inside the folder, as in any folder they can write to, and `CreateNew` never replaces what they put there (tested with a file planted at a page's name; a hard link is an ordinary entry the same way). That it also refuses a dangling symbolic link at the name, rather than creating its target, is expected from NTFS but not tested, since creating one needs Developer Mode or admin rights; T18 should check it on such a machine. `PdfToImages` and `DevSplit` write this way, with `FileShare.None`.

Alternatives rejected for this part: **a private DACL on the temporary folder** would stop other accounts entirely. But the result must end with the permissions it inherits beside the input, and resetting them means propagating inheritance through files at the final name, where links could be planted. **`NtCreateFile` with `FILE_CREATE`** would close the short window between creating and opening. It still does not stop an in-place junction, and the check through the handle already catches a swap in that window. **Recursing into subfolders by handle** would need an anchor in every subfolder. No writer makes subfolders.

### Progress within a file

`IOperation` gains a second `RunAsync` overload as a **default interface member**:

```csharp
Task<string> RunAsync(string inputPath, IProgress<FileProgress>? progress, CancellationToken ct) => RunAsync(inputPath, ct);
```

The runner always calls this overload. An operation without progress implements only the old method and inherits the default, so nothing existing changes. An operation with progress implements the new one and makes the old one call it with `null`. `FileProgress(unit, position, total)` is a validated record ("page", 1…total); the runner turns each report into a `BatchProgress` with `Within` set and `Current` naming the file, under the same lock as the start and end reports, so a page report always falls between them; a report arriving after the file finished is dropped. The progress window shows `BatchProgressText.DescribeWithin` ("page 37 of 200") on a second line, cleared when a file starts or finishes; the bar still counts files. The line's accessible name carries the text with its context ("Progress in the current file: page 37 of 200"), so UI Automation reads it. It is not a live region, so a screen reader does not announce 200 pages one by one.

`dev.split` (Dev > Split into pages, `install-menu --dev`) writes 50 page files into a folder with a page report each (`FLEVERT_DEV_PAGE_MS` per page), to exercise both parts end to end.

## Alternatives considered

- **An optional interface** (`IReportsFileProgress`) the runner tests for: works too, but adds a type test in the runner and a second place to look for what an operation can do. The default member keeps a single contract, and the runner has one call site.
- **Changing the one `RunAsync` to take progress**: breaks every operation and every test, and collides with the parallel v0.2 work, for no gain over a default member.
- **`IProgress<double>`** (the spec's first idea): a fraction cannot say "page 37 of 200", and every operation would have to agree on what 1.0 means. A unit, a position and a total cover pages, frames and images, and the window can still derive a fraction if it ever needs one.
- **An operation context object** (progress, cancellation, options in one parameter): more flexible, but a larger change than v0.2 needs; it can still come later as another default member.
- **Moving files one by one into the final folder** instead of renaming the folder once: a crash midway leaves a partial folder under its final name, which is exactly what has to be avoided.

## Consequences

- Operations that report progress must not make the two overloads call each other through the default (that would recurse); the XML documentation on `IOperation` says so.
- An operation decides how often it reports. One report per page is fine for rendering; an operation that could report thousands of times a second should report less often, since every report reaches the window's message loop.
- A folder output can take up to about 30 s longer to finish while a scanner holds a page, with the last page report still showing. If the scanner holds it longer, the result is a visible `.flevert-<guid>.partial` folder with every page in it and a failure naming it; the user renames it. A crash still leaves a hidden `.partial` folder with pages in it (sweeping old ones is optional work for T18), but never the anchor.
- The runner still lets go of a cancelled file at once rather than awaiting it (unchanged). An operation that honours the token deletes its temporary folder at its next token check, while the progress window and notification keep the process alive; one stuck in a long native call when the process exits could still leave a `.partial` folder, as a `.partial` file could before.
- `BatchProgress` gained an optional `Within` parameter; existing code that constructs it is unchanged.

## Part 2: many inputs, one output

### Context

Merging PDFs and combining photos into one PDF take every selected file and write **one** output, in the order Explorer shows the names (docs/specs/pdf.md, "Thay đổi ở core" item 1). Explorer still starts one `flevert.exe` per file, in no reliable order (ADR-0002), so the batch leader is the only process that ever sees the whole selection. Requirements: nothing runs until the batch is complete; every file stays pinned for the whole run; one file that cannot be used fails the whole output, naming it, with no partial output; per-file operations behave exactly as before.

### Decision

**Contract.** The members the menu, the catalog and `list-ops` need move to `IMenuOperation` (`Id`, `MenuPath`, `Extensions`). `IOperation` extends it and is otherwise unchanged, so no existing operation or test changes. A new `IBatchOperation` extends it too:

```csharp
Task<string> RunAsync(IReadOnlyList<string> inputPaths, IProgress<FileProgress>? progress, CancellationToken ct);
```

`inputPaths` holds at least one path: the real, pinned, distinct paths in natural order. The operation writes beside `inputPaths[0]` through `OutputPath`, decides whether one file is enough (merge refuses it, combining photos accepts it), and throws `BatchInputException(inputPath, message)` to name an input it cannot use. `OperationCatalog` holds `IMenuOperation` and refuses an operation that is both kinds or neither, since `run` picks the code path by kind. The menu entry is the same per-file command as before (`run <id> "%1"`).

**Collecting the batch.** `BatchLeader.ReadAllAsync` ends only when the consumer is idle, nothing is queued, no trusted sender delivered paths for the idle window, and the batch is at least 1.5 s old; at that moment the pipe closes and the key rotates (ADR-0002). The runner for a batch operation reads that stream **to its end** before doing anything else, and only then pins. For a join the leader also waits for the rest of its selection and nothing ever joins a file alone: see "No partial output" below (F5). The first version of this part relied on a 1 s idle window alone; at that window the join split under load (measured below).

**Pin all, then sort, then run once.** Every file goes through the same checks as a per-file input (`Reject`, `InputPin.TryPin`, the extension of the real path). All pins are kept until the operation returns. Two spellings of one file (a short 8.3 name and the long one) pin the same real path and are joined once. The real paths are sorted with `NaturalOrder.PathComparer`: Windows' `StrCmpLogicalW` (shlwapi, through `LibraryImport`) on the file name, then on the whole path, then ordinal, so the order is total and the same however the files arrived. `StrCmpLogicalW` is what Explorer sorts with (the `NoStrCmpLogical` policy switches Explorer back to plain text order), so pages come in the order the user sees.

**All or nothing.** If any file is rejected, the operation is not called. Every rejected file is logged with its own reason; the single result names the first in natural order, plus how many more were rejected. A `BatchInputException.ForInput(path, message)` names the file in the result (the constructor taking a path is private: a path and a message are both strings and were easy to swap); one built with the standard constructors names no file, and like any other exception fails the output with its message. A batch that received no file fails with "No files were received." rather than "Done: 0 files". The log keeps the stack trace after the first line, and the notification shows only that first line, cut to 120 characters so the log folder still fits.

**Outcome.** `BatchOutcome { OneOutput = true }` with `Total` 1 and one result (none when cancelled). Notification: `Done: <output name>`, `Failed: <file>: <reason> Details: <log folder>`, `Skipped: <reason>` or `Cancelled.`. The exit codes of core.md hold: the leader exits 0 when the output was written or skipped, 1 when it failed or was cancelled; followers exit 0 once their files are delivered. A successful join logs one line per input with the output, so the log still has every path processed.

**Progress.** One "file" for the batch line: `0 of 1 done: <first file>` at the start, the operation's reports as the second line ("file 3 of 12" for `dev.join`), `1 of 1` at the end, under one lock so no report shows after the end.

**Cancellation.** While files are still arriving, nothing runs. During the run the operation gets the token and up to 2 s to stop and delete its temporary output, then it is abandoned and the pins are released (a per-file operation is let go at once, unchanged). If it finished writing its output within those 2 s, the output exists: it is reported (`Done: …`) and logged like any finished join, not as "Cancelled.".

### No partial output (F5, 2026-10-20)

**Measured.** 100 `dev.join` processes started within 1 s at the product window, with 24 busy loops on a 16-core machine: 1, 3, 22, 64, 56, 27, 57, 52, 39 and 65 outputs in ten runs (12 processes still gave one output in 8 of 8). Traces showed why: the leader serves one sender at a time (170-250 ms per exchange under load), so 64 followers hit the 10 s join deadline and joined their own file alone; startup took 0.7 to 13 s per process. When the shell itself starts the processes (`MenuProbe invoke` on 100 files), it created them in 2.1 s idle and in 18.6 s under load, at most 0.5 s apart. Separately, two copies of flevert.exe sharing one key file split each other's batches (ADR-0002). Each extra output was partial and the main one silently missed those files.

**Decision.** For a batch operation, `Batch.LeadOrJoinOneOutputAsync` replaces `LeadOrJoinAsync`; per-file operations are unchanged.

- **Hand-over for up to 60 s, never alone.** 100 senders took about 25 s under load.
- **The leader waits for its selection.** Explorer creates every process before any of it runs, and a process's creation time and command line exist from that moment (`ProcessFacts`). A census (`ProcessCensus`) lists the running flevert.exe processes of the same operation that would pass the peer check (same executable, session, integrity not lower), with their files. While one of them on the leader's chain (below) has not delivered, the batch stays open, up to 30 s after the last delivery; the idle window for a join is 3 s (it only has to cover the gap between two creations).
- **One selection = one chain of creation times** with gaps of at most `JoinGate.ChainGap` = 2 s, starting from the leader's own (the shell's gaps: 0.5 s at most under load). The leader admits a sender only if its creation time is on that chain (members, census and sender included) and not before the previous batch's close; otherwise it answers the new reply `Late` (4). A selection made while another batch of the operation collects is therefore not merged into it.
- **A record beside the key** (`pipes\<op>.<scope>.join`): written "open" when a leader starts, and "closed" with the close time and every member just before the pipe name is released (also when the name was lost), so whoever gets the name after the close reads it. A process that would lead is **late** if it was created before the last close. If the record is open and its leader still runs, the name was free only for a moment (the leader was replacing its pipe instance, or the key moved): the process gives the name back and waits for the leader's pipe as a sender, so its file is joined rather than left out; the leader retries for 2 s, and a process that never reaches it is left out after the 60 s hand-over deadline. If the record is open and its leader is gone, it died while collecting and the files it held are lost: a process created within 30 s of that leader (`JoinRecord.SelectionSpan`; the shell took 18.6 s for 100 processes under load) is late, so the rest of that selection is reported instead of joined into an output that looks complete; a later selection is on time. A member whose acknowledgement was lost exits 0 silently. A close in the future (the clock went back), an unreadable, damaged or other-version record counts as none, in the record and in the leader's gate.
- **Late files are reported, never joined.** A late process, a sender answered `Late` or `Full`, refused twice, past the 60 s deadline or without a key, hands its files to the batch `<op>#late` (same timings, no gate). Its leader writes nothing, logs each file and ends with one notification: `<file> and N more files were left out: they arrived while Flevert was joining other files. Select the files again.`, exit code 1; if even that batch cannot be reached, the process reports its own files.
- **A process that dies before handing over** (killed, out of memory, Windows could not start it) was seen by the census: the join fails, naming its file (`… never reached Flevert, so nothing was joined.`), instead of writing the rest.
- The leader of a join retries re-creating its pipe instance for 2 s before giving up the name: a process of its own selection that took the free name finds the open record, lets go at once and hands its file over as a sender.

**Numbers kept.** Idle window 3 s, chain gap 2 s, hold 30 s after the last delivery, hand-over 60 s, a dead leader's selection 30 s. A join of one file starts about 2 s later than before (3 s instead of 1 s idle).

**Verified** at the product window (no `FLEVERT_BATCH_IDLE_MS`): 12 and 100 processes give one file; a process created with the others but resumed after 6 s is waited for; one created 2.6 s later and resumed after the close is left out with no second output; a second selection started 2.6 s after the first, while it collects, is left out and not merged; a process killed before handing over fails the join and is named; two joins run back to back both work; two copies of flevert.exe at once each give one output. The four behaviour tests fail with the old wiring. Under the same load as above, 100 processes gave one output in 12 of 13 runs; the other exposed a follower crash (`InvalidOperationException` from the client's pipe-owner check, ADR-0002) that turned into a failed join naming the lost file, and was then fixed. After the rebase on 2026-10-20, real processes on an idle machine, headless: 10 + 1 created together with one resumed after 6 s gave one output of 11; 10 + 1 started 2.6 s later, and 10 + 1 created 2.6 s later and resumed after the close, each gave one output of 10 and the late process exited 1 with its file logged as left out.

**Alternatives considered.** A longer idle window alone (3 s still split under load in a parallel test run, and does nothing for the 10 s deadline); counting the selection (Explorer passes no count, and its selection cannot be read reliably); spool files instead of the pipe (rejected in ADR-0002); several pipe instances in parallel (would raise throughput, but changes how ADR-0002 elects a leader; left for later); a time slack after the close for "late" (it refused scripts that run joins one after another, and the census already waits for slow starters); letting a second selection wait and then lead its own batch (it needs the chain of the closed batch, and a shell pause longer than the chain gap would then split one selection silently instead of with a message).

`dev.join` (Dev > Join, `install-menu --dev`) concatenates `.txt` files into `<first name> (+N).txt`; one file gives `<name> (joined).txt`, since "(+0)" reads like a mistake.

### Alternatives considered

- **A "batch complete" signal or a collect phase in `BatchLeader`**: the end of `ReadAllAsync` already means that, decided by the close logic that ADR-0002's reviews hardened. A second mechanism would duplicate it and could disagree with it.
- **Starting the join with the files that are there and appending late ones**: the order is not known until the batch is complete, and a file arriving later could sort first.
- **Pinning each file only when the operation reads it**: a file could be replaced between sorting and reading, and all-or-nothing requires every file to be checked before anything is written.
- **.NET's numeric string comparison** (`CompareOptions.NumericOrdering`) instead of `StrCmpLogicalW`: managed and portable, but not guaranteed to match Explorer, which is the whole point. Matching Explorer includes its limits (below).
- **Sorting by the paths as received**: an 8.3 name (`IMG_00~1.JPG`) would sort by its short form; the real path is the name the user sees.
- **Extending `IOperation` with a list overload**: every per-file operation would carry a member that means nothing for it, and the runner could not tell the kinds apart without a flag.

### Consequences

- The menu is unchanged; the per-file path (followers, leader, runner) is unchanged (its whole test suite still passes). A join's leader and followers take the path above.
- A late file is reported, never joined (F5). **Residual risks, accepted:** if the shell pauses for more than the 3 s idle window in the middle of creating one selection's processes after all earlier ones delivered, the rest forms a second batch and a second output; if it pauses for more than 2 s while the batch still collects, the rest is left out with a message. Neither was seen (0.5 s at most under load). Two selections whose processes are created within 2 s of each other are taken as one. A leader that crashes while collecting loses the files already handed to it (ADR-0002); the rest of its selection is left out with a message, and so is a new selection started within 30 s of that leader. A process the census cannot see (it could not be queried) is neither waited for nor reported missing. A selection of more than 1000 files is answered `Full` and its extra files are left out, which the menu cannot reach (Explorer shows it for at most 100 files).
- The "left out" and "never reached" notifications are tray balloons like every other result; Focus Assist can hide them, and the log has every file.
- A user who chooses the same join again while one is still collecting gets "left out" and must select the files again once it has finished.
- **Explorer's order, with its limits** (checked on this machine): a tone or a stroke counts after letters and numbers ("Ảnh 2" sorts before "anh 3", "đ" between "d" and "e"); digit runs compare by value up to 18 digits, longer ones fall back to text order; the comparison follows the user's locale. Tests pin the behaviour that holds in every locale.
- A join holds one handle per input (at most 1000) until it finishes.
- An operation that ignores the token is abandoned after 2 s and may then read inputs that are no longer pinned, as an abandoned per-file operation can.
