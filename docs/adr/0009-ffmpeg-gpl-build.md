# ADR-0009: Video and audio with the GPL build of ffmpeg, run as a separate program

## Status

Accepted

## Date

2026-10-20

## Context

v0.3 converts, compresses and extracts video and audio (docs/specs/media.md). Videos arrive from phones and strangers, so whatever parses them must be maintained and patched; ffmpeg is the only engine that reads every source type of the spec. Flevert is MIT and never links GPL code into its own process (CLAUDE.md). Binaries are never committed and releases are built only by GitHub Actions (ADR-0005).

Options checked on 2026-10-20:

- **BtbN/FFmpeg-Builds** publishes Windows builds of ffmpeg in GPL and LGPL variants, static or shared, for each release branch. Daily builds are kept 14 days; the last build of each month is kept two years (its README, "Release Retention Policy"); `latest` moves every day. Each release lists the SHA256 of its assets in `checksums.sha256`.
- The **LGPL** variant has no libx264. H.264 would then come from `h264_mf` (Media Foundation): no constant quality, no two passes, and quality that depends on each machine's encoder, so "Under 25 MB" could be neither promised nor tested.
- Both variants oblige whoever distributes them to provide the corresponding source (LGPL 2.1 sections 4 and 6 for ffmpeg and its LGPL libraries; the GPL variant adds x264 and the other GPL libraries).
- Wrappers (docs/specs/media.md, "Tham khảo trước khi viết"): FFMpegCore (MIT) starts ffmpeg itself, outside `ExternalTool`'s job, memory limit and tree kill, which are security requirements here; it was only a reference for reading `-progress`, and no code was taken. Xabe.FFmpeg has a non-commercial licence; HandBrakeCLI (GPL, about 40 MB) duplicates ffmpeg; FileConverter (GPL) was not read. The two-pass bitrate and GIF palette recipes come from ffmpeg's own documentation (the H.264 encoding guide, `palettegen`).

## Decision

- **The GPL build**, shared variant, of **FFmpeg 8.1.3** (`n8.1.3-9-g29e619e767`) from BtbN's release `autobuild-2026-09-30-13-08`, the last build of September: `ffmpeg-n8.1.3-9-g29e619e767-win64-gpl-shared-8.1.zip`, SHA256 `dfe81c3aa0a546ee81980b1b824486dd0fe0a1d452f00cb55135379a74be7bcf` (as in the release's `checksums.sha256`; downloaded and computed again on 2026-10-20). The user approved GPL over LGPL on 2026-10-20 (docs/specs/media.md, Open Question 1). The build's own licence is GPL version 3 (`--enable-version3`).
- `scripts/fetch-deps.ps1` fetches it into `deps/ffmpeg` like pdfium and qpdf (ADR-0008) and keeps `ffmpeg.exe`, `ffprobe.exe`, the seven DLLs they share (199 MB unpacked, about 46 MB more in the installer) and `LICENSE.txt`; not `ffplay.exe`, headers or import libraries. `Flevert.Media.csproj` copies them into an `ffmpeg` folder beside `flevert.exe`, and the installer installs that folder without unpacking it for setup's location check. CI checks that the version line of the fetched `ffmpeg.exe` names the pinned commit.
- **A separate program.** Flevert only starts `ffmpeg.exe` and `ffprobe.exe` through `ExternalTool` (a job that dies with flevert.exe and lets them start no process of their own, 4 GB of memory each, a timeout, below normal priority). The spec asked for 2 GB; x264 at preset medium alone takes about that for 4K60, an iPhone's usual setting (3 s of 4K60 peaked at 2.2 GB in SDR and 2.5 GB in HLG on 4 cores, and takes 11 times real time there), so 2 GB would refuse the users' own videos and reads their output. Nothing of ffmpeg is linked into Flevert, which stays MIT: the two are an aggregate.
- **Untrusted input**, because the build carries network protocols (libcurl, OpenSSL, libssh, SRT, RIST, ZeroMQ) and script demuxers (AviSynth, VapourSynth):
  - the input is always `file:<full path>`, after `-protocol_whitelist file`, so its name can never select a protocol and nothing it contains can open one;
  - `-format_whitelist mov,matroska,avi,asf,mpegts,mp3,wav,flac,ogg,aac,aiff` allows only the demuxers of the spec's source types (ffmpeg matches it with `av_match_list`, so `mov` is `mov,mp4,m4a,3gp,3g2,mj2`), so a playlist, a concat list or a script named `.mp4` is refused by ffprobe before anything is converted (MaliciousMediaTests; without the demuxer whitelist, a concat list naming the real video beside it is read);
  - every option is Flevert's own (constants and numbers it computed), passed one by one; nothing a file says reaches the command line except metadata values, each a single `key=value` argument, from an allowlist of tags; no filter that reads a file (`movie=`, `amovie=`, `subtitles=`) is ever used;
  - only the first video stream (never cover art) and the first audio stream are written; subtitles, data streams and attachments never are;
  - ffprobe refuses a file with no stream, no duration, more than 12 hours or a picture past 8K; each pass has a timeout of six times the duration plus a minute (twelve for VP9); `-fs` stops an output past four times the input plus 100 MB (or twice what the duration calls for), and reaching it is an error;
  - `-fs` is never more than the room on the output's disk past 50 MB, for encodes and stream copies alike (re-check review, RC2-3), so a file that holds more than its header claims (a FLAC whose header says 2 s over an hour of sound) cannot fill the disk; reaching it is an error; Remove hidden info's `-fs` is the input plus 5 % and 10 MB (the same streams in less metadata). Converting sound checks for the space its duration calls for, but its `-fs` takes the duration to be at least as long as the file's bytes last at 32 kbit/s, since ffprobe only estimates how long a raw AAC or an MP3 without a VBR header is (RC2-4, RC3-1);
  - a video encode also stops after 1.5 times the duration ffprobe read plus 10 s, or as long as the file's bytes last at 8 kbit/s if longer (`-t`), so a file cannot hide much more than ffprobe read. That floor lets a crafted file claim up to its bytes ÷ 1000 seconds, so for such a file the timeout, not `-t`, is the real bound on the run and on x264's statistics, which no `-fs` covers (RC2-5); ffmpeg reaching that bound is an error, never a cut output passed for the whole. Sound and stream copies are not bounded by time: ffprobe only estimates the length of a raw AAC, of an MP3 without a VBR header, or of MPEG-TS recordings joined byte by byte (5 minutes read as 30 s), and `-fs` bounds them (re-check review, RC-1);
  - the timeout grows with the pixel rate (6 × the duration for 1080p30, 48 × for 4K60) and doubles for HDR, which is tone mapped in floating point, up to 200 × and two days at most: it only stops a run that is stuck;
  - x264 runs at most 12 threads and the decoder 8 (fewer on smaller machines, as each chooses itself): memory grows with them, and 3 s of 4K60 HLG peaked at 4.5 GB with the 24 and 13 a 16-thread PC gets, and at 3.2 GB with 12 and 8, as fast (re-check review, RC-2);
  - `FFREPORT` and `AV_LOG_FORCE_*` are removed from ffmpeg's environment.
  - Not done in v0.3.0: a decoder whitelist (`-codec_whitelist`), which the security review recommended to shrink what an untrusted file can reach. Its list must cover every codec of the source types and the subtitle, cover-art and data codecs a file may carry, or ffprobe refuses ordinary files, and it can only be checked against the shipped 8.1 build on Windows: listed for the next release.
- **The corresponding source.** `scripts/fetch-ffmpeg-source.sh` writes `ffmpeg-source-<tag>-<n>-of-<count>.tar` from the pins under `ffmpegSource` in `scripts/deps.json`: FFmpeg at commit `29e619e767cde9045a75c29bc9a8278ae7b3a98b`, BtbN's build scripts and patches at `6c9aec5fc9a72ec3abedd1fa84db141fa18cf52b` (the commit of the release tag), and each of the 101 libraries the `win64 gpl-shared 8.1` build enables, fetched by BtbN's own `download.sh` in BtbN's tooling image built from that commit, so every library comes from the git commit, SVN revision, submodules and vendored crates the build used. `release.yml` runs it on Linux (Docker) through `ffmpeg-source.yml` and attaches the archive to every release beside the setup, with a line in the release notes; GitHub refuses an asset of 2 GiB or more and the whole source is 2.2 GB, so it is split into as many tars as keep each under that (the first holds FFmpeg and BtbN's scripts, the libraries follow in name order), each whole on its own, all extracted into one folder giving one tree described by the README.txt in each; a single library past the limit fails the run. This replaces the `scripts/fetch-ffmpeg-source.ps1` the spec named: BtbN's download needs Docker with Linux containers, which the Windows runners lack.
- **Licences.** The same script collects the licence files of FFmpeg and of each library (`COPYING*`, `LICENSE*`, `COPYRIGHT*`, `NOTICE*` anywhere in its source but its history and test data, so the code a library bundles, such as librsvg's vendored crates, is covered too); they are committed under `installer/notices/ffmpeg/`, named after the build stage (`50-x264-COPYING`), and `scripts/write-notices.ps1` puts them in `THIRD-PARTY-NOTICES.txt` after the FFmpeg entry. The libraries whose terms live only in their source files' headers (nv-codec-headers) are listed by the script, and their terms are written out there by hand. `ffmpeg-source.yml` runs on every pull request that changes the pin, uploads the licences as an artifact, and fails while a licence file of the build is missing from `installer/notices/ffmpeg/` or differs, or while the FFmpeg notice in `scripts/deps.json` does not list that folder (it lists BtbN's `LICENSE.txt` alone until the files are committed, so the tests that run the notices script on the real manifest pass meanwhile); the release fails the same way, and lists the archive's SHA256 in `SHA256SUMS.txt`. The toolchain's runtime that the build links statically (mingw-w64's CRT and winpthreads, whose stage is in the archive; GCC's libgcc and libstdc++ under the GCC Runtime Library Exception) needs no source beyond that.

- **Frame times.** Every video encode passes `-fps_mode passthrough` (frames closer together than the stream's nominal rate allows then reach x264 with the same time, which ffmpeg corrects with a warning: a synthetic edge case, RC-8): ffmpeg otherwise picks per container, passthrough for the first pass (`null`) and constant frame rate for MP4, so a phone's variable frame rate gave the second pass frames the first never saw, and ffmpeg 6.1 hung there (code review, CR-3).
- **Remove hidden info** copies the streams (`-c copy`), but an H.264 stream from a camcorder also loses its SEI messages (`filter_units=remove_types=6`): camcorders keep the camera, the time and the place there (Sony and Panasonic's MDPM), which ffprobe does not show as tags (security review, SEC-2). ffmpeg can only drop every SEI, recovery points included, by which a stream without keyframes (a dashcam's intra refresh) is seeked (re-check review, RC-3): so only where a camcorder's data is, in an AVCHD file (`.mts`, `.m2ts`) or in any file whose first 8 MB hold MDPM's SEI user data (its UUID, then `MDPM`: 20 bytes no picture holds by chance, RC3-3), as an AVCHD clip remuxed to MP4 or MKV does (RC2-1). Camcorders write MDPM in every GOP, so the first megabytes show it; a faststart MP4 of several hours, whose index comes first and passes 8 MB, is missed (RC3-2, accepted: rare, and reading further costs every file its time). Choosing by keyframes instead was tried and fails: x264's intra refresh marks its recovery points as keyframes in MP4. Its pictures decoded from the start are the same, its packets no longer byte for byte the input's, as docs/specs/media.md asked (criterion 13), which privacy outweighs there. Other H.264, whose SEI then holds at most an encoder's settings or recovery points, and HEVC, whose SEI carries the HDR mastering data, are copied whole. MP4, MOV, 3GP, AVCHD and any H.264 file always get their copy instead of a skip, since they can hold what ffprobe does not show (XMP, makers' boxes, SEI).

## Consequences

- The installer grows from 47 MB to about 94 MB (LZMA2, measured on the ffmpeg folder with `xz -9e`); docs/specs/media.md allows 150 MB.
- Each release carries a source archive of possibly a gigabyte or more, written by a two-hour job; the BtbN tooling image is built from the pinned commit, its base image and packages from their archives on the day.
- Dependabot cannot follow BtbN's builds: a monthly check for a new FFmpeg release (docs/RELEASING.md) moves the pin to the newest month-end build, with its SHA256, the `ffmpegSource` pins and the licences the pull request's artifact brings.
- A month-end build is deleted after two years, so a release older than that can no longer be rebuilt from the pin; its source archive stays attached to it.
- Unicode paths, `\\?\` long paths, x264's statistics file under a Vietnamese user name, the priority, and ffmpeg dying with flevert.exe are checked on Windows only (FlevertExeTests, test-installer.ps1): the media tests run elsewhere with the system's ffmpeg and without job objects.
